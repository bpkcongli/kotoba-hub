# Backend boundaries

Use this for `IMP-02`–`IMP-10`, backend work in `IMP-17`, or a backend review.

1. Find the task ID in [task breakdown](../../../docs/task-breakdown.md), then read its linked sequence, ERD, and API documents. Resolve mismatches before changing the affected flow.
2. Keep `src/app/api/v1/**/route.ts` as transport delegation. Implement REST controllers in every context as classes in `interface/primary/rest`, with endpoint operations as methods and use-case dependencies injected through the constructor. A controller instance may be exported from its controller file. Route handlers call instance methods through a wrapper or explicit binding to preserve `this`; never store request-specific data on a shared controller instance. Put business decisions in `src/backend/<context>/domain` or `application`; adapters live in `interface`/`infrastructure` as specified in [ARCHITECTURE.md](../../../ARCHITECTURE.md). Consolidate each context's dependency composition in one `infrastructure/di/index.ts` file; consumers import from `infrastructure/di`. Module ownership and business flow follow [architecture foundation](../../../docs/architecture-foundation.md).
3. Use application ports/facades for context crossings. `syllabus` owns catalog and skill identity, `progress` owns events and snapshots, `users` owns learner profiles, `personalization` owns recommendation policy, `flashcards` and `practice` own activity flow.
4. Follow `/api/v1` paths, session guards, response envelope, pagination, and error-code conventions from [API base](../../../docs/api-contract/README.md) and the feature OpenAPI file. Treat request payloads as untrusted and validate them at the boundary.
5. Keep database ownership consistent with the ERD; avoid cross-context repository reads/writes. When a requirement needs a new field or flow, update the relevant docs/contracts with the implementation.
6. Model DDD concepts explicitly: use classes for value objects (validate invariants when creating them), entities (stable identity), aggregates (enforce consistency boundaries), domain services, application service implementations, and repository implementations. Keep application service contracts, repository contracts, and application ports as interfaces; keep transport DTOs, Drizzle schemas, and serializable snapshots as plain data. Place each context's custom exceptions and their detail types in `domain/exceptions`; use cases and transport adapters import those domain definitions. Follow the placement rules in [ARCHITECTURE.md](../../../ARCHITECTURE.md). The [crud-products-nextjs example](https://github.com/Developer-Marcelo/crud-products-nextjs) illustrates class-based domain models and repository implementations; project docs remain authoritative for KotobaHub behavior and layout.
7. Name persistence interfaces `<Entity>Repository` and place them in `domain/repositories/<entity>.repository.ts`; do not use the `Port` suffix or `application/ports` for persistence contracts. Name Drizzle implementations `Drizzle<Entity>Repository` in `interface/secondary/persistence/drizzle-<entity>.repository.ts`. Reserve outbound application ports for required service/facade dependencies, context crossings, and non-persistence dependencies; provided service APIs use the service interfaces described below. A context crossing must use the owning context's application service/facade, which delegates persistence to its domain repository interface.
8. Define explicit request DTOs for endpoint inputs that need parsing or validation (body, path, query, or relevant headers) and response DTOs for returned data. Keep HTTP DTOs and their mappers in `interface/primary/rest`; keep use-case request/response models in `application` when they differ. Validate untrusted input before invoking the use case, and map output field by field to the OpenAPI schema so internal fields cannot leak. Redirect-only and empty-data responses need no artificial payload DTO.

## Application service contracts

- For new or refactored application services, name the interface `<Name>Service` and place it in `application/services/<name>.service.ts`. Name the class `<Name>ServiceImpl implements <Name>Service` and place it in `application/services/impl/<name>.service.impl.ts`. Do not use an `I` prefix or `Contract` suffix for this interface.
- Controllers, adapters, and collaborating services depend on service interfaces through type imports. The context's DI creates `Impl` instances and exports them with explicit interface types. Implementation tests may instantiate `Impl` classes; keep private methods out of service contracts and preserve the public operations needed by existing consumers.
- Service interfaces describe operations provided by the context; outbound `Port` interfaces describe dependencies required by its use cases. Keep these roles and locations distinct. Use personalization's `ConfirmAssessmentService`/`ConfirmAssessmentServiceImpl` and syllabus's service pairs as examples. Apply migrations only within the assigned contexts; do not rename unrelated existing service/port contracts solely to enforce this convention.

## Consumer-owned cross-context ports

- When an outbound port belongs to the consumer context, keep it in `<consumer>/application/ports`. Implement it explicitly with a class in `<consumer>/interface/secondary/<provider>/<name>.adapter.ts`; the consumer use case depends on the port, and the adapter calls the provider's application service/facade.
- Wire provider facade -> consumer adapter -> consumer use case in the consumer's `infrastructure/di/index.ts`. Do not inject the facade directly into a consumer-owned port using structural typing, or make the provider import/implement the consumer's port. Map provider data when the consumer contract differs; preserve the documented dependency direction and avoid provider repository/table access.
- Use `personalization`'s `SyllabusCatalogPort` and `SyllabusCatalogAdapter` as the concrete example in [ARCHITECTURE.md](../../../ARCHITECTURE.md). Provider-owned public facade contracts may still be implemented inside their owning context; this convention does not require moving existing provider-owned ports or refactoring unrelated integrations.
